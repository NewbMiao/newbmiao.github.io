Ownership is one of Rust’s most distinctive features — and one of the hardest for newcomers.

Ownership trips up most Rust beginners. The examples below show what it is, why the compiler cares, and how move, borrow, and lifetimes fit together. Skim once for the map; come back for the line-by-line bits.

Move or copy?

Both look like “assign this value to another variable more than once” — once for the number a, once for the string d. Only the string case breaks.

That’s Rust’s split between copying a value and moving ownership.

When you pass a value to another variable or function: if the type implements Copy, Rust duplicates it; otherwise ownership moves.

a is an integer; integers are Copy, so code 1 compiles.

d is a String; strings are not Copy. The first assignment moves ownership to _e. You only get one move, so code 2 fails.

Why copy or move at all? Spoiler: Rust has no garbage collector (GC). Memory is tied to ownership — whoever owns a value is responsible for freeing it when the value is dropped.

  • A value has exactly one owner; when the owner leaves the scope, the value is dropped.
  • Ownership can be transferred.

That model makes manual memory management tractable.

Can you mix mutable and immutable borrows like this?

No:

The compiler is explicit: while a mutable borrow is active, you can’t also hold immutable borrows.

Think read–write lock: a mutable borrow is like holding the write lock — no concurrent readers, or your writes and their reads could disagree.

Borrowing rules, summarized:

  • You can have many immutable borrows.
  • At most one mutable borrow at a time, and it excludes immutable borrows.

Ownership rules

All three ownership principles are on the table now:

  • Each value has exactly one owner; when the owner leaves its scope, the value is dropped.
  • Ownership can be transferred.
  • Borrowing:
    • Many immutable borrows allowed.
    • One mutable borrow at a time (exclusive with immutable borrows).

These rules define who owns a value, when memory can be freed, and what mutation and sharing are allowed — no dangling use-after-free, and no torn reads during writes (no data races on shared data in the single-threaded borrow-checker sense).

The striking part: the compiler enforces this before you ship. Crashes in production with a late stack trace are worse.

Lifetimes

Last topic: lifetimes.

Why doesn’t this compile?

Error:

Two borrowed parameters, one borrowed return — the compiler can’t tell which input the return might outlive.

Enter lifetimes: annotations that describe how long references must remain valid, so borrows don’t dangle.

If inputs and output share one lifetime 'a, the returned reference can’t live longer than both inputs — as long as the inputs are valid, the return is valid. If the return could point at something created only inside the function, it would become a dangling pointer after the function returns.

You can picture a lifetime as an extra parameter on a reference, telling the compiler whether that reference is still in-bounds for a given scope.

Side note: Go’s escape analysis solves a related problem — values that must survive the stack frame get heap-allocated. That’s also lifetime reasoning, but with a GC underneath. Rust prefers compile-time lifetime proofs; Box helps when you need heap ownership across scopes (not expanded here).

Does every reference need a label?

No. The compiler infers lifetimes in most code. You only add them when inference clashes. For the deep end, see Subtyping and Variance.

Summary

Wrapping up:

  • Ownership is about who owns values and when memory is freed.
  • The borrow checker enforces that borrows are valid at compile time.
  • Lifetimes describe how long references must stay alive.

Together they give Rust strong memory safety without a GC — fewer leaks, fewer dangling pointers, and less runtime overhead from collection.

If you’re curious, the ownership story is worth the learning curve: one coherent model instead of implicit rules scattered across the language.
