Go protobuf upgrade — github.com/golang/protobuf to google.golang.org/protobuf

Contents

  1. 1. Round one
  2. 2. Round two
  3. 3. Round three

A recent protobuf dependency bump looked routine—until CI and protoc disagreed.

Dependabot suggested moving github.com/golang/protobuf from v1.3.5 to v1.4.0.

Round one

I expected a straight version bump. CI failed: tests called generated XXX_Size() to measure message size; on v1.4.0 that path panics.

Compare old vs new generated code. Proto source: official helloworld.proto.

Generate v1.3.5 output:

Swap in protoc-gen-go@v1.4.0 and regenerate. Search for XXX_Size.

Old codegen still wires it through InternalMessageInfo:

New .pb.go no longer defines InternalMessageInfo; the type still exists in the module as deprecated:

Use proto.Size(m Message) int instead. InternalMessageInfo became the protoiface.MessageV1 interface alias. Release notes: v1.20 generated code.

Swap the call sites—round one done.

Round two

Docs for github.com/golang/protobuf v1.4.0 say maintenance moves to google.golang.org/protobuf. Fine—upgrade the gRPC plugin too.

Regenerate. The new plugin wants:

option go_package = ".;helloworld";

Then failure:

Try the new flag:

Still failing:

protoc-gen-go-grpc is a separate binary. gRPC stubs used to come from protoc --go_out=plugins=grpc:.

Install attempt:

Another miss:

pkg.go.dev lists protoc-gen-go-grpc; the protobuf-go repo did not ship it yet. Issue thread: plugins are not supported: grpc.

google.golang.org/protobuf shipped new protoc-gen-go without the gRPC plugin; protoc-gen-go-grpc was still in review (not stable at the time).

Official workaround: keep generating gRPC with the old github.com/golang/protobuf toolchain—or reuse gengogrpc from the in-flight plugin; see comment.

Round three

Runtime on google.golang.org/protobuf@v1.21.0, codegen with github.com/golang/protobuf/protoc-gen-go@v1.4.0. Regenerate—finally green.

Generated imports looked split:

Still pulling both protobuf module families felt wrong. Unless you need the new APIs now, waiting is reasonable.

The breaking changes were intentional: first-class reflection and new tooling—see v1.21.0 release.
