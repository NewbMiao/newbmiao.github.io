Strings look simple. They mostly are—start with what the compiler does for +.

0x01 How + is lowered

go tool compile -m folds literal runs:

Assembly (-S | grep concat):

Pipeline:

  • Fold constant string fragments at compile time ("y" + "x" + "z" → "yxz").
  • Pass remaining operands to concatstringN / concatstrings.
  • Arity 2–5 → concatstring2…concatstring5; more → slice concatstrings.
  • Total length < 32 → stack tmpBuf to skip a heap alloc.

0x06 Concat benchmarks

Short (16 B) vs long (256 B) strings, few vs many joins: concat_benchmark.

sprint/sprintf/Join builds are pre-sized lists; +, Builder, Buffer loop and append.

  • Prebuilt args: sprint ≈ sprintf; strings.Join wins (uses Builder internally).
  • Looping +: cost grows quickly with count.
  • Few joins: strings.Builder beats bytes.Buffer; many joins the gap flips—check alloc counts.

Builder did more allocations per op in the test because Reset() drops storage:

Builder forbids aliasing after String() (copyCheck). Both types benefit from one upfront Grow—see concatIterWithGrowInit in the repo.

After Grow, alloc counts drop to 1 per op and Builder leads, matching the docs.
