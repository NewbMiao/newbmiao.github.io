AI 搞 Terraform，怎么管才不会翻车？

千丈之堤，以蝼蚁之穴溃；百尺之室，以突隙之烟焚。 - 韩非子·喻老

现在让 AI 写 IaC 已经不算新鲜事。补一个 Module、改几个资源、顺手生成 Policy，速度通常比人工快得多。

麻烦也跟着变了。一次改动可能混进无关资源，语法完全正确的 Terraform，也可能带来 Delete、Replace 或权限放宽。这些问题不一定能在 Code Review 里一眼看出来。

代码越来越多，全部靠人逐行检查不太现实；把 Review 再交给 AI，也只是多了一层判断，并没有多一层保证。

其实根本问题是：AI 可以继续写、继续试，但它的错误怎么被稳定地发现，又怎么避免进入生产环境？

核心思路

在我看来，解决问题可以收成三步：先限定 AI 能改什么，再用脚本和 Policy 验证结果，最后把生产写操作留给人工审批和 CI/CD。

范围内的代码可以让 AI 自己生成、小步提交、根据报错返工。格式、语法、变更范围和 Plan 风险由脚本检查，基础设施规范由 Policy 检查。

受控分支里的代码修改和生产写操作分开处理。AI 可以修改代码；合并代码、修改生效中的规则和变更生产环境，由人批准，再交给 CI/CD 执行。

flowchart TD
    A["人定义任务、权限和资源范围"] --> B["AI 在受控分支小步提交"]
    B --> C["脚本检查 Commit 和 Scope"]
    C --> D["fmt / validate / lint"]
    D --> E["Terraform Plan"]
    E --> F["tfpolicy + Plan 脚本检查"]
    F --> G{"检查通过？"}
    G -- No --> H["返回明确错误"]
    H --> B
    G -- Yes --> I["保存 Plan 和检查报告"]
    I --> J["人工审查并批准"]
    J --> K["独立 CI/CD Identity 执行 Apply"]
    K --> L["tfpolicy Apply 阶段检查"]
    L --> M["Azure Policy / Runtime 检查"]
    M --> N["监控、Drift 检查和规则改进"]

1. 先把活动范围圈出来

AI 不需要只能改几行代码，但每个任务应该有明确的范围。

比如这次只调整一个数据库连接，就不应该顺手修改其他资源或者大范围重构 Module。

Do

  • 任务开始时明确允许修改的文件、Module 和 Resource。
  • 使用独立身份，限制 Git、Cloud 和 Terraform Enterprise 权限。
  • 在隔离的 Runner 中执行 Plan，只提供完成 Plan 所需的只读 Cloud 和 State 权限。
  • 默认禁止修改 CI Workflow、CODEOWNERS、检查脚本和生效中的 Policy。
  • 把修改拆成小提交，每个 Commit 只处理一件事，方便逐段审查和回退。
  • 用脚本比较基准 Commit 和当前分支，检查每个 Commit 是否超出文件和资源白名单。
  • 如果确实需要改范围外的资源，先让人确认，再更新任务范围。

Don’t

  • 不要把 Prompt 或 AGENTS.md 当成权限系统。
  • 不要给 AI 生产环境的 Apply、Destroy 和 State 修改权限。
  • 不要因为需要生成 Plan，就提供完整的生产 Cloud 凭据。
  • 不要把多个无关修改堆进一个大 Commit。
  • 不要因为一个任务需要更多权限，就顺手放开整个 Stack。

2. 能用脚本检查的，就别让 AI 自己判断

代码生成可以交给 AI，基础检查没必要也交给 AI。

这些检查不需要模型理解业务，也不应该每次依赖模型给出结论。

Do

  • terraform fmt -check 检查格式。
  • terraform validate 检查配置是否合法。
  • TFLint 检查常见 Terraform 配置问题。
  • Checkov 补充安全扫描。
  • 自定义脚本检查文件、命名、版本和资源范围。
  • 所有关键检查都返回明确的成功或失败，能脚本化的尽量脚本化。

Don’t

  • 不要用 AI 的自查结论代替工具结果。
  • 不要让 AI 跳过失败项，或者自行把失败解释成可以接受。
  • 不要让本地和 CI 使用两套不同的检查标准。

本地检查可以让 AI 快速返工，CI 检查则负责最终把关。两边尽量使用同一套脚本和规则，避免本地通过、提交后却被另一套标准拦住。

3. 基础设施规范放进 tfpolicy

格式和语法只是代码层面的检查。真正涉及基础设施安全和平台规范的规则，应该由 Policy 统一管理。

如果当前环境支持 tfpolicy，可以逐步迁移已有规则。

Do

  • Setup 阶段限制 Provider 和 Module 的来源及版本。
  • Plan 阶段检查资源属性、网络、安全、IAM 和 Tag。
  • 检查资源之间的关系，例如 Storage Account 是否配置了 Private Endpoint。
  • Apply 阶段检查只有资源创建后才能确定的属性。
  • 给重要规则准备应该通过和应该失败的测试。

Don’t

  • 不要把规范只写在 Prompt 或 Wiki 里。
  • 不要把 tfpolicy Apply 阶段检查当成持续的 Runtime 监控。
  • 不要在业务 Terraform PR 里顺手修改强制 Policy。
  • 不要为了统一工具，把仍然有价值的安全扫描全部删掉。

工具可以逐步收敛，但规则迁移要确认语义一致。重复的规则可以合并，尚未覆盖的检查继续保留。

4. Plan 不只看合规，还要看这次到底改了什么

tfpolicy 能判断资源是否符合平台规范，却不一定知道这次工单原本想改什么。

比如工单只是修改一个 Storage Account 的 Tag，Plan 却出现了数据库替换。这种变更可能符合资源规范，但显然不符合任务预期。

这部分可以用脚本补上。

Do

  • 使用 terraform show -json 导出 Plan。
  • 用 jq 提取资源地址和具体 Action。
  • 将实际变更与任务预先定义的资源范围比较。
  • 普通修改任务出现 Delete，默认拦截。
  • 出现 Replace，要求额外审批。
  • 发现范围外的资源变化，直接失败并反馈原因。

Don’t

  • 不要只看 AI 生成的 Plan 摘要。
  • 不要默认允许整个 Stack 被修改。
  • 不要把 -target 当成权限边界或日常用法。

-target 只留给故障恢复或少数特殊场景。它不能代替变更检查，使用后仍要补跑完整 Plan，确认没有遗漏依赖或其他变化。

5. 代码可以改，生产环境不能直接碰

前面几步解决的是代码和变更是否符合预期。接下来要解决的是：谁有权真正改变基础设施？

代码修改、生产授权和生产执行分开处理：AI 修改受控分支，人批准具体 Commit 和 Plan，CI/CD 执行生产写操作。

Do

  • AI 在受控分支生成代码，并在隔离 Runner 中运行检查和 Plan。
  • CI 保存具体 Commit 对应的 Plan 文件和检查报告。
  • 人审查 Diff、Plan 和报告，再决定是否批准。
  • 独立 CI/CD Identity 执行批准过的 Plan，例如 terraform apply tfplan。
  • Apply 使用的 Plan 必须与审批时的 Plan 一致。

Don’t

  • 不给 AI Merge、Apply、Destroy 或 State 修改权限。
  • 不让 AI 审批自己的修改。
  • 不让 AI 修改 CI Workflow、审批规则或其他放行条件。
  • 不要在审批后重新生成 Plan，再执行另一份未经审核的内容。

这样 AI 可以在代码层面快速迭代，真正写入云环境的动作则始终经过独立流程。

6. Apply 之后，Runtime 检查继续跑

tfpolicy 的 Apply 阶段检查随 Terraform 执行结束，之后的持续合规、资源状态和 Drift 交给 Azure Policy 与监控系统。

Do

  • 用 Azure Policy 等云端能力持续检查资源合规性。
  • 定时运行 Terraform Plan 检查 Drift。
  • 监控资源状态、安全风险和成本变化。
  • 把线上发现的问题反馈到 Module、脚本和 Policy。

Don’t

  • 不要发现 Drift 就自动 Apply。
  • 不要覆盖故障处理或安全团队留下的合法变更。
  • 不要只看 Pipeline 是否成功。

发现 Drift 后，先确认变更来源和影响，再决定接受、修复还是恢复。自动发现可以做，自动覆盖不一定合适。

7. AI 可以帮忙写 Policy，但不能自己批准 Policy

AI 不只可以写业务代码，也可以帮我们编写治理规则。

它可以把平台规范转成 tfpolicy、生成测试，或协助迁移已有的 Sentinel / OPA 规则。它也可以发现缺失的防线：当重复出现的评审意见或生产事故暴露出同类问题时，AI 可以提议新的 Policy、校验或回归测试。

提议不等于生效。它必须包含正反用例测试，由平台或安全负责人评审，并通过独立的治理 PR 合并。这样才能形成从工程实践和历史故障到新规则的反馈闭环，同时由人决定哪些规则成为强制要求。

但 Policy、CI Workflow、CODEOWNERS 和检查脚本都属于治理配置，不能夹在业务代码 PR 里一起改。

Do

  • 业务 Terraform 和 Policy 分开提 PR。
  • Policy 变更同时提交正向和反向测试。
  • 通过 CODEOWNERS 交给平台或安全工程师审批。
  • CI Workflow、CODEOWNERS 和检查脚本的修改也走独立审批。
  • 规则合并后，重新检查受影响的业务 PR。

Don’t

  • 不让 AI 自动合并 Policy PR。
  • 不让 AI 批准自己的规则或豁免申请。
  • 不让业务 PR 同时修改放行条件。
  • 不要把测试全绿当成规则一定正确。

测试通过只能说明规则符合已有用例，不能证明规则本身正确。AI 可以起草和修正规则，但规则是否合理、是否放宽了原有要求，仍然需要人来确认。

落地顺序

先收掉 AI 的生产写权限，把文件和资源范围限制好；然后补齐 fmt、validate、Lint、Commit、Scope 和 Plan 检查；再把已有的基础设施规范逐步迁到 tfpolicy。

链路跑稳后，再让 AI 协助编写 Policy。范围内可以放手让它尝试；越过代码边界的动作，仍由人批准和负责。
