Most of us have at least heard of OAuth2.

New to the vocabulary? Skim Authentication vs authorization — OAuth2, OIDC, JWT, and Keycloak for the basics and flows.

With Google as the IdP, the usual story: user hits the consent screen, comes back with an authorization code, you exchange it for tokens, then call Google APIs on the user’s behalf.

Rolling that by hand isn’t huge — but add Facebook, Instagram, and every other IdP and you don’t want N custom integrations. A central auth layer is the point. Here we use Keycloak as that layer.

If you can’t reproduce it locally, it’s hard to learn or debate the design. This walkthrough uses Rust/Axum + Keycloak, with docker-compose, Terraform, and shell scripts so you can replay the whole stack on a Mac. Repo: https://github.com/NewbMiao/axum-koans

OAuth with Google first

Before Keycloak, walk through plain Google OAuth so the brokered flow has something to compare against.

Prerequisite: a Google OAuth client clientId and clientSecret. See Create a Google Application in How to setup Sign in with Google using Keycloak.

In the authorization code flow, the client and auth server mainly do two things:

  • Build an auth URL; after login, receive a code to exchange for tokens
  • In the callback, swap the code for credentials — typically accessToken (and often refreshToken)

You can wire this yourself; in practice people use an OIDC client (OpenID Connect on top of OAuth2 — standardized user identity for apps).

Option 2: broker stored tokens

What about the Google refresh token itself?

Some clients refresh Google access tokens on their own. They shouldn’t need a Keycloak access token first just to fish out Google’s refresh token.

Use Retrieving external IDP tokens: Keycloak persists external tokens at login; grant the user broker read token and you can read stored external access + refresh tokens with a Keycloak access token.
