Go runtime memory pool

Overview

Go manages memory for you: a heap allocator plus the GC. Most of the time you never touch malloc yourself. Below: the pool allocator in the runtime (Go 1.10.3) and how the pieces connect.

The design follows tcmalloc (thread-caching malloc): per-thread caches for small objects (≤32 KiB), then central lists, then the heap, then the OS. Tiered caches shrink lock contention and fragmentation.

Below: how memory is carved up, the main structs, then the allocation path in source.

Memory layout

At init the runtime maps one contiguous region and splits it into spans metadata, bitmap, and arena (runtime/malloc.go).

On 64-bit (pointer size 8 bytes):

  • Arena — the heap pool (~512 GiB virtual).
  • Bitmap — which arena words hold objects and whether they contain pointers; 1 byte covers 4 pointer slots (2 bits per pointer) → ~16 GiB metadata.
  • Spans — one pointer slot per 8 KiB heap page → ~512 MiB.

Data structures

mspan

A run of contiguous pages for a given size class — the basic allocation unit. The stack pool also chains mspan values (runtime/stack.go) to cut stack alloc cost for goroutines.

Notable fields:

  • freeindex — index of next free slot in [0, nelems); slots before it are allocated.
  • allocBits — bitmap of free slots (1 = free).
  • allocCache — complemented bits from freeindex for fast ctz scanning (sys.Ctz64).
  • spanclass — size class + noscan flag.
  • elemsize — object size for size class; page multiple for large spans.

mcache

Per-P cache (only one M holds a given P at a time) — no lock for small allocs. alloc holds 67 *mspan buckets (local cache).

  • alloc — one active span per span class.
  • tiny / tinyoffset — bump pointer for sub-16 B tiny objects.

class_to_size in sizeclasses.go lists byte sizes per class (8, 16, … up to 32768).

mcentral

Central free lists per size class. mcache refills from nonempty; may sweep spans; if still empty, asks mheap.

mheap

Owns virtual arena addresses; small and large objects; global stats.

  • freelarge — treap of large free spans (best-fit; see mgclarge.go).
  • spans — page index → mspan.
  • central — array of mcentral.

Allocation flow

Allocate

  • > 32 KiB — large object from mheap.
  • < 16 B — tiny allocator in mcache (packed tiny objects, with alignment rules 8/4/2/1 byte). Some waste, faster access.
  • 16 B … 32 KiB — pick sizeClass, alloc from mcache.alloc[class].
  • mcache miss → mcentral → mheap (best-fit span, split remainder) → OS (≥1 MiB pages).

Free

Object returns to mcache; may flush to mcentral then mheap. Sweep: mspan.sweep in runtime/mgcsweep.go.

Source trace

mallocgc (abbreviated behavior):

  • Tiny (noscan, size < maxTinySize): align tinyoffset, bump in current tiny block or grab new span; zero 16 bytes when starting fresh block.
  • Small: map size → sizeclass, nextFreeFast or mcache.nextFree → refill chain.
  • Large: largeAlloc → mheap.alloc.

nextFreeFast uses allocCache and Ctz64.

mcache.nextFree calls refill → mcentral → mheap → sysAlloc.

largeAlloc rounds to pages, mheap_.alloc, sets limit.

Summary

Go tiers allocation: tiny bump buffer, size-class spans in per-P caches, central lists, then heap pages from the OS. Fixed size classes limit fragmentation; caching amortizes locks and syscalls.

  • Tiny (<16 B): mcache tiny allocator
  • Small (16 B–32 KiB): size class + mcache / mcentral
  • Large (>32 KiB): mheap directly
