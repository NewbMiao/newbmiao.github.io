Rust shared ownership — Rc, Arc, and weak references

One owner

Rust’s ownership model says each value has one owner. When the owner goes out of scope, the value is dropped.

In the snippet below, if a is moved into b, you cannot print a afterward — ownership already moved.

Deep copy (clone)

clone gives you a second allocation. It works, but it is not cheap.

Reference counting (Rc)

Multiple owners without copying the payload each time — use reference counting via Rc.

Each clone bumps the count. When it hits zero, drop runs and memory is freed.

Copy-on-write

The data inside an Rc is immutable through shared handles. To mutate in place, Rc::make_mut checks the strong count: if other live references exist, it clones the inner value and edits the clone; otherwise it mutates in place. That is copy-on-write — pay for a copy only when you need to diverge.

Edits stay isolated from older clones. If you want mutations visible through every handle, pair Rc with Cell or RefCell for interior mutability.

Reference cycles

Cycles break naive reference counting: counts never reach zero, so memory leaks.

Weak references

Weak does not increment the strong count, so it cannot keep a cycle alive by itself.

A weak pointer may dangle once strong count hits zero. Call upgrade() for an Option<Rc<T>>.

Lifetime still follows strong references only.

Thread safety

Rc is not thread-safe. For sharing across threads, use Arc (atomic reference counting).

To mutate shared data on multiple threads, wrap the inner type in Mutex or RwLock, e.g. Arc<Mutex<T>>.

One more detail: both Rc<T> and Arc<T> deref to T, so you can call T methods on the smart pointer. To avoid ambiguity with T’s own methods, people often call smart-pointer methods with full qualification, e.g. Rc::clone.
