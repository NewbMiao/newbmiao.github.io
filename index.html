AI-Driven Terraform: Move Fast Without Losing Control

AI 搞 Terraform，怎么管才不会翻车？

Having AI write IaC is no longer unusual. It can add a module, change a few resources, and draft policy much faster than a person.

That speed brings a different problem. A change can pull in unrelated resources. Terraform that is perfectly valid can still delete or replace resources, or loosen permissions. Those issues are not always obvious in code review.

As the volume grows, reviewing every line by hand stops scaling. Handing the review to another AI adds another opinion, not another guarantee.

The real question is this: how can AI keep writing and iterating while its mistakes are caught consistently and kept out of production?

千丈之堤，以蝼蚁之穴溃；百尺之室，以突隙之烟焚。 - 韩非子·喻老

现在让 AI 写 IaC 已经不算新鲜事。补一个 Module、改几个资源、顺手生成 Policy，速度通常比人工快得多。

麻烦也跟着变了。一次改动可能混进无关资源，语法完全正确的 Terraform，也可能带来 Delete、Replace 或权限放宽。这些问题不一定能在 Code Review 里一眼看出来。

代码越来越多，全部靠人逐行检查不太现实；把 Review 再交给 AI，也只是多了一层判断，并没有多一层保证。

其实根本问题是：AI 可以继续写、继续试，但它的错误怎么被稳定地发现，又怎么避免进入生产环境？

If you’ve planned a VNet, you know the drill. Wiki holds the “official” diagram. Excel is where you actually try cuts. IPAM kicks in once people agree on addresses. That’s fine until you need to split a /22 three different ways the night before a meeting.

I just wanted something you could open, chop up, undo, and send to someone—without hunting down who changed which /27 two weeks ago.

做网络规划的人，大概都维护过子网。

有人放在 Wiki，有人放在 Excel，也有人用云上的 IPAM 或 IP Range Manager。各有各的用处，但真要临时调整网段，总觉得不够顺手。

Wiki 适合记结果，不太适合来回试。一个人改了 CIDR，另一个人补了备注，过两周再打开，先得同步线上确认最新的。

Excel 灵活，大家也熟。只是网段一多，表格很快就从「规划」变成「考古」：这一段是谁留的，为什么是 /27，旁边还能不能继续拆，都得回头翻聊天记录。

云上的 IPAM 更适合管已经定下来的地址。开会前想把一块 /22 换几种切法看看，用它又有点重。

我想要的只是一个趁手一点的工具：打开就能切，切完就能给别人看。

Still, a Reddit thread on clickops vs IaC nudged me to write down how I think about Terraform as an ops person right now.

I first touched Terraform on an AWS project in 2019. Declaring infra in code felt like cheating in the best way.

I was mostly dev then, but everything after that gravitated toward Terraform—Aliyun, GCP, Azure, the whole tour.

事无定势，因时制宜。

Rust typestate — compile-time checks for OAuth2 client setup

Rust设计模式：typestate

Typestate encodes lifecycle state in the type system.

oauth2-rs uses it for a concrete pain point: OAuth2 clients need auth_url, token_url, introspect_url, and friends wired up before auth calls make sense. If token_url is missing, exchanging an authorization code for a token fails at runtime.

Forgot to call set_token_url? You find out when you fetch a token—not when you build the client.

Typestate pushes that mistake to compile time.

今天聊聊typestate模式。

新版oauth2-rs使用这个模式是想解决一个问题。

在Oauth2中，一般需要提前配置好auth_url, token_url, introspect_url等，才能调用后续的鉴权相关功能。比如没有token_url配置好，你就无法成功拿授权码（code）获取token。

但如果用户忘了配置，那就会在调用获取token时才得到运行时错误。

能不能在编译时就把错误暴露出来，让用户提前感知问题？

这就是typestate模式能很好解决的问题。
