OPA bundles — package policy and data for distributed OPA servers

A bundle is how OPA ships policy and data as one artifact. The engine was built for sidecars and daemons in cloud-native setups, so distribution, updates, and observability show up early — not as an afterthought.

Bundles cover:

  • Central config for policy + data
  • Hot(ish) policy refresh without redeploying every consumer
  • Health, metrics, and decision logs from many OPA instances

With Rego on top, that’s what makes OPA feel like a general policy layer instead of a one-off authz library.

Below: bundle layout, server APIs, remote bundle config, embedding options, and metrics. There’s a docker-compose demo in the koans repo—run it locally once you’ve skimmed the sections.

OPA server APIs

Before bundle-specific endpoints, the REST API surface:

API Purpose
Data Query rules and virtual documents
Policy Read compiled policy
Query Ad-hoc query execution
Compile Partial evaluation
Health Liveness
Metrics Prometheus text

Spin up server mode on the quick-start tree:

Paths are under /v1/; data queries under /v1/data/.

Default decision path is data.system.main — then the POST body is input, not wrapped. Override: opa run --server --set=default_decision=example_rbac/allow quick-start and curl -s http://0.0.0.0:8181/ -d @quick-start/input.json

Data API also accepts explain, metrics, provenance, etc. — see docs when debugging.

Bundle management APIs

Four channels aimed at fleets of OPAs:

  • Bundles — poll and pull tarball updates
  • Decision logs — upload gzipped log batches (size-partitioned, traceable by log id)
  • Status — periodic heartbeat with metrics snapshot
  • Discovery — central OPA config; nodes sync and then pull the right bundles
