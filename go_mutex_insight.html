Go sync.Mutex — normal mode, starvation mode, and the runtime wait queue

Contents

  1. 1. Overview
  2. 2. Implementation
    1. 2.1. Lock
      1. 2.1.1. Spinning
    2. 2.2. Unlock
  3. 3. Wait queue
  4. 4. References

Overview

sync.Mutex is a semaphore-style lock: acquire decrements availability; release increments and may wake one waiter.

Layout:

Starving mode avoids goroutines stuck behind endless barging.

  1. Normal mode — FIFO wait queue, but a woken waiter races newcomers; newcomers often win because they are already on-CPU.

  2. Starvation mode — after ~1 ms waiting, newcomers queue only (no spin, no steal). Unlock hands the lock directly to the front waiter.

  3. Back to normal when wait time < 1 ms or the wait queue is empty.

Implementation

Lock

Fast path: CAS 0 → locked. Slow path: lockSlow().

Spinning

Spinning is limited (at most four active spins) and only when:

  • Multiple CPUs
  • GOMAXPROCS > 1 + (idle P + spinning M)
  • Local run queue empty

Unlock

Drop locked bit; slow path wakes a waiter or starvation handoff.

That covers Lock/Unlock; waiters live in the runtime semaphore tables.

Wait queue

runtime/sema.go implements acquire/release. Waiters hang off a treap (semaRoot.treap) of sudog nodes:

  • Distinct elem pointers in the treap
  • Blockers on the same Mutex share &m.sema as elem
  • ticket orders a min-heap; same-address waiters link via waitlink, tail in waittail

Lookup for one mutex address is O(1); scanning distinct addresses in a bucket is O(log n). Table size 251 (semTabSize).

Why pad sized cpu.CacheLinePadSize - sizeof(semaRoot)? Hint: false sharing between semtable slots on adjacent cache lines.
